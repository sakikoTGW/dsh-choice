# dsh-choice

把「给用户留选择」的收尾交给 DSH **原生提问卡**：回合结束后弹出一张卡，列出 2–4 个候选，外加一个「先看看，待会再做」。

## 触发条件

一条助手消息的最后是一个 **2–4 项的 Markdown 列表**、**并且列表前面那段话是在请你拍板**（以问号结尾，或带「要不要 / 哪个 / 哪种 / 选 / 二选一 / 你来定 / 两条路…」这类选择语境）时，才算请用户做选择：

```text
两种都行，看你想要哪种。

- 装 dsh-steer，用现成的
- 保留 dsh-guide，接管主对话框
```

「下一步：1. 装 2. 保留 3. 先不动」这种普通结尾列表**不会**弹卡——列表只是列表，不是选择题。

另外识别三种短句二选一：`要么 A，要么 B`、`A 也行；B 也行`、面向用户且以问号结尾的 `A 还是 B？`。列表在消息中间、只有一项、超过四项，都不触发。

## 提示词只在该拍板的回合注入

插件注册的是**动态** systemPrompt section：只有用户这条消息本身带选择语境（问「选哪个 / 要不要继续 / 用哪种」）时，才把「用 2–4 项列表收尾」那条提示注入给模型；普通执行类消息不注入。

> 0.2.2 修的就是这里：0.2.1 每轮无条件注入，模型会把**每一轮**回复都写成候选列表，于是每轮都弹卡（"必须跳"）。现在提示词和弹卡都只在真正需要拍板的回合出现。

识别发生在 `assistant/message`；真正提问发生在 `turn/end` 且回合正常完成之后——不会和正在跑的回合抢输入框。

## 为什么用原生卡

弹卡是宿主能力：`ctx.userQuestions.ask()` 走 `user-questions/request` waterfall，DSH Web 客户端自己会把提问卡挂到输入框位置、渲染选项、处理选中/跳过/自由输入。插件只做三件事：

1. 识别收尾里的选项；
2. 调 `ask()` 发一张带选项的原生问题；
3. 拿回答案后，把选中的标签作为一条用户消息发出。

所以没有自绘 UI，也不需要客户端代码。

## 交互

| 卡片元素 | 行为 |
|---|---|
| 2–4 个候选 | 点一个：把它作为你的消息发出，开启下一回合 |
| 先看看，待会再做 | 只收起卡片，不发消息 |
| 自由输入 | 你写的文字原样作为消息发出 |
| 跳过 / 关闭 | 不发消息 |

用户手动发消息、或新回合开始时，仍挂着的提问会被 abort，卡片收起。

## 数据通道

没有 HTTP 路由。全部通过宿主服务：

| 调用 | 用途 |
|---|---|
| `ctx.userQuestions.ask({questions, agent, signal})` | 发原生提问并等待回答 |
| `ctx.agents.get(sessionId)` | 确认会话有存活的根 Agent |
| `agent.followup()` / `agent.steer()` | 投递用户的选择 |

## 回滚

自绘胶囊条版本留在 `client.js`（当前未从 `package.json` 导出、也没有 `dsh.client` 声明，所以不会加载）。要回到那一版：恢复 `exports["./client"]` 与 `dsh.client` 清单项，并把 `client.js` 加回 `files`。

## 实现边界

- Host 只监听 `session/event`（`assistant/message`、`turn/start`、`turn/end`、`user/message`）与 `agent/disposed`。
- 不 import 任何 `@deepseek-ai` 包。
- 只处理纯文本、不含 tool-call 的助手消息；被中断的消息不参与。
- 提问只对存活的根 Agent 发起；子代理会话不会弹卡。

## 已知限制

- 选择语境判定是启发式的：带「要不要/哪个/还是/你定…」或问号才算；纯「下一步 / 建议」列表按普通列表处理，不弹卡。
- 散文式二选一（例如「如果你想要现成的装 A 也行；我这个的差别是 B」）里的 B 不会被解析出来——宁可不弹，也不给错选项。
- 原生卡是**阻塞式**的：它会临时占用输入框，等你选或关。运行中引导（dsh-guide）则是非阻塞的，两者互不影响。
- 卡片由 DSH 客户端渲染；没有客户端连接时 `ask()` 会失败，插件静默放弃。
